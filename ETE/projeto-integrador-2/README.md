## 🔄 Metodologia de Trabalho — Scrum Adaptado para Sala de Aula

### Framework Scrum na Escola

O Scrum será aplicado de forma adaptada à realidade escolar, com sprints de **2 semanas (4 aulas)** e cerimônias ajustadas ao tempo de aula.

### ⏱️ Cerimônias Adaptadas

| Cerimônia | Quando | Duração | O que acontece |
|-----------|--------|---------|----------------|
| **Sprint Planning** | 1ª aula do Sprint | 15 min | Equipe seleciona itens do Backlog para o Sprint |
| **Daily Standup** | Início de cada aula | 5 min | Cada membro responde: O que fiz? O que vou fazer? Tem impedimento? |
| **Sprint Review** | Última aula do Sprint | 20 min | Demo do que foi construído para a professora |
| **Sprint Retrospective** | Após a Review | 15 min | O que deu certo? O que melhorar? Ações concretas. |

### 📦 Artefatos Scrum

| Artefato | Ferramenta | Descrição |
|----------|------------|-----------|
| **Product Backlog** | Trello | Lista priorizada de TODAS as funcionalidades do produto |
| **Sprint Backlog** | Trello (lista separada) | Itens selecionados para o Sprint atual |
| **Burndown Chart** | Planilha simples ou manual | Gráfico de trabalho restante vs tempo |
| **Definition of Done (DoD)** | Documentação do time | Critérios para considerar um item "pronto" |

### 👥 Papéis Scrum

| Papel | Quem | Responsabilidade |
|-------|------|------------------|
| **Product Owner (PO)** | Profª Luana Cristina | Define prioridades, aceita/rejeita entregáveis |
| **Scrum Master** | Rodízio a cada Sprint | Facilita cerimônias, remove impedimentos |
| **Dev Team** | Todos os membros | Desenvolve, testa e documenta o produto |

> ⚠️ **Importante:** O papel de Scrum Master é rotativo! Cada membro da equipe deve exercer esse papel pelo menos uma vez durante o semestre.

### ✅ Definition of Done (DoD) Padrão

Para um item do backlog ser considerado **DONE**, deve atender:

- [ ] Código funcional e sem erros
- [ ] Código versionado no GitHub (branch + merge via Pull Request)
- [ ] Testes básicos realizados
- [ ] Documentação atualizada (se aplicável)
- [ ] Revisado por pelo menos 1 colega de equipe
- [ ] Demo realizada para o PO (professora)

## 📝 Template de User Story

Todas as funcionalidades devem ser escritas no formato de User Story:

```
Como [tipo de usuário]
Eu quero [ação/funcionalidade]
Para que [benefício/valor]

Critérios de Aceite:
- [ ] Critério 1: descrição clara do comportamento esperado
- [ ] Critério 2: validação necessária
- [ ] Critério 3: feedback visual para o usuário

Definição de Pronto:
- [ ] Código implementado e testado
- [ ] Pull Request aprovado
- [ ] Demo realizada
```

### Exemplo Prático

```
Como administrador da biblioteca
Eu quero cadastrar novos livros no sistema
Para que o acervo esteja sempre atualizado

Critérios de Aceite:
- [ ] Formulário com campos: título, autor, ISBN, ano, editora, categoria
- [ ] Validação: todos os campos obrigatórios preenchidos
- [ ] Validação: ISBN com formato válido (13 dígitos)
- [ ] Mensagem de sucesso após cadastro
- [ ] Livro aparece na listagem após cadastro

Definição de Pronto:
- [ ] Tela de cadastro funcionando no Tkinter
- [ ] Service validando os dados
- [ ] Repository salvando no PostgreSQL
- [ ] Teste unitário do Service passando
```

> 🎯 **Regra:** Cada equipe deve ter no mínimo **10 User Stories** no Product Backlog ao final do Sprint 0.

## 📊 Rubrica de Avaliação Final

### Critérios Detalhados

| Critério | Peso | Excelente (9-10) | Bom (7-8) | Insuficiente (0-6) |
|----------|------|-------------------|-----------|---------------------|
| **Produto Funcionando** | 30% | Aplicação completa, estável, sem bugs críticos. Todas as funcionalidades do backlog implementadas. UX agradável. | Aplicação funciona com pequenos bugs. Maioria das funcionalidades implementadas. Usável. | Aplicação com erros graves, crashes frequentes ou funcionalidades essenciais ausentes. |
| **Documentação Técnica** | 20% | README completo, diagramas UML atualizados, manual do usuário claro, código bem comentado. | Documentação presente mas incompleta ou desatualizada em relação ao código final. | Documentação ausente, incompreensível ou completamente desatualizada. |
| **Processo Scrum** | 20% | Trello organizado, sprints bem definidos, cerimônias realizadas, burndown atualizado, DoD respeitado. | Processo Scrum parcialmente seguido, algumas cerimônias puladas, Trello desorganizado. | Não seguiu o Scrum, sem evidências de gestão ágil, trabalho desorganizado. |
| **Qualidade de Código** | 15% | Código limpo, bem organizado em camadas (Repository/Service/GUI), nomes significativos, sem repetição. | Código funcional mas com alguma desorganização, mistura de responsabilidades. | Código confuso, sem padrão, copy-paste excessivo, impossível de manter. |
| **Apresentação Final** | 15% | Apresentação clara, objetiva, demo ao vivo sem problemas, equipe preparada, respondeu perguntas com segurança. | Apresentação razoável, demo com pequenos problemas, respostas parciais às perguntas. | Apresentação confusa, demo falhou, equipe não soube explicar o projeto. |

### Fator de Participação Individual

O fator individual (0.5 a 1.2) é calculado com base em:

| Evidência | Como é verificada |
|-----------|-------------------|
| Commits no GitHub | Histórico de contribuições (quantidade e qualidade) |
| Participação nas Dailies | Registro da professora |
| Avaliação por pares | Formulário anônimo entre membros da equipe |
| Presença nas aulas | Frequência registrada |
| Papel de Scrum Master | Desempenho quando no papel de facilitador |

## 🌟 Dicas de Ouro para o Sucesso

### Para a Equipe
1. **Comecem simples** — Primeiro faça funcionar, depois melhore
2. **Commits frequentes** — Commit toda aula, no mínimo
3. **Comuniquem-se** — Grupo no WhatsApp/Discord para dúvidas rápidas
4. **Dividam bem as tarefas** — Use o Trello para que todos saibam quem faz o quê
5. **Peçam ajuda cedo** — Não esperem ficar travados por 2 semanas
6. **Testem sempre** — Um bug descoberto cedo é 10x mais fácil de resolver

### Para o Scrum Master da vez
1. **Mantenha o foco** — Daily de 5 minutos, não de 30
2. **Atualize o Trello** — Mova cards durante a aula
3. **Proteja o time** — Se alguém está com dificuldade, ajude a resolver ou escale para a professora
4. **Documente impedimentos** — Registre no Trello o que está bloqueando

### Para quem está com dificuldade
1. **Pair Programming** — Programe junto com um colega mais experiente
2. **Revise o material anterior** — As disciplinas do Módulo 2 cobrem tudo que precisa
3. **Google + Stack Overflow** — Pesquisar é uma habilidade profissional
4. **Horário de atendimento** — Procure a professora nos horários disponíveis

## 🤝 Contrato de Equipe

No início do projeto, cada equipe deve preencher e assinar um "Contrato de Equipe":

| Item | Acordo |
|------|--------|
| **Horário de comunicação** | Ex: WhatsApp das 8h às 22h |
| **Ferramenta de comunicação** | Ex: WhatsApp + Discord |
| **Frequência de encontros extras** | Ex: 1x por semana fora da aula |
| **O que acontece se alguém não entregar** | Ex: Primeiro conversa, depois reporta à professora |
| **Como resolver conflitos** | Ex: Votação democrática, Scrum Master media |
| **Compromisso de qualidade** | Ex: Ninguém faz merge sem review |

> 🎯 **Por quê?** Acordos claros evitam conflitos. Equipes que combinam regras no início têm menos problemas no final.
