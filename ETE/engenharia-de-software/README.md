### 1. Scrum — Framework Ágil

O Scrum é um framework ágil para gerenciamento de projetos complexos. Organiza o trabalho em ciclos chamados **Sprints** (geralmente 2-4 semanas).

#### Ciclo do Sprint

```
┌─────────────────────────────────────────────────────────────────┐
│                        CICLO SCRUM                               │
│                                                                  │
│  ┌──────────┐    ┌──────────────┐    ┌─────────────────────┐   │
│  │ PRODUCT  │───▶│   SPRINT     │───▶│      SPRINT         │   │
│  │ BACKLOG  │    │  PLANNING    │    │  (2-4 semanas)      │   │
│  └──────────┘    └──────────────┘    │                     │   │
│                                       │  ┌─────────────┐   │   │
│                                       │  │   DAILY     │   │   │
│  ┌──────────┐    ┌──────────────┐    │  │  STANDUP    │   │   │
│  │INCREMENT │◀───│   SPRINT     │◀───│  │ (15 min/dia)│   │   │
│  │(Entrega) │    │   REVIEW     │    │  └─────────────┘   │   │
│  └──────────┘    └──────────────┘    └─────────────────────┘   │
│                         │                                        │
│                         ▼                                        │
│                  ┌──────────────┐                                │
│                  │ RETROSPECTIVE│                                │
│                  │ (Melhoria)   │                                │
│                  └──────────────┘                                │
└─────────────────────────────────────────────────────────────────┘
```

#### Papéis do Scrum

| Papel | Responsabilidade |
|-------|-----------------|
| **Product Owner (PO)** | Define o que será feito; prioriza o Product Backlog; representa o cliente |
| **Scrum Master (SM)** | Facilita o processo; remove impedimentos; protege o time |
| **Development Team** | Equipe auto-organizada (3-9 pessoas); entrega o incremento |

#### Cerimônias (Eventos)

| Cerimônia | Quando | Duração | Objetivo |
|-----------|--------|---------|----------|
| **Sprint Planning** | Início do Sprint | 2-4h | Definir o que será feito no Sprint |
| **Daily Standup** | Todo dia | 15 min | Sincronizar o time (O que fiz? O que farei? Impedimentos?) |
| **Sprint Review** | Final do Sprint | 1-2h | Demonstrar o incremento aos stakeholders |
| **Sprint Retrospective** | Após Review | 1-1.5h | Melhorar o processo do time |

#### Artefatos

| Artefato | Descrição |
|----------|-----------|
| **Product Backlog** | Lista ordenada de tudo que é necessário no produto |
| **Sprint Backlog** | Itens selecionados do Product Backlog para o Sprint atual |
| **Incremento** | Soma de todos os itens completados no Sprint (potencialmente entregável) |

> 💡 **Dica**: O Product Backlog é um documento vivo — é constantemente refinado e repriorizado pelo PO.

### 2. Casos de Uso

Os Casos de Uso descrevem **como** os usuários (atores) interagem com o sistema para atingir um objetivo.

#### Template de Caso de Uso

```
╔══════════════════════════════════════════════════════════╗
║              CASO DE USO: [Nome]                         ║
╠══════════════════════════════════════════════════════════╣
║ ID:              UC-XXX                                  ║
║ Ator Principal:  [Quem inicia]                           ║
║ Pré-condição:    [O que precisa ser verdade antes]       ║
║ Pós-condição:    [Estado do sistema após execução]       ║
╠══════════════════════════════════════════════════════════╣
║ FLUXO PRINCIPAL:                                         ║
║ 1. Ator faz X                                           ║
║ 2. Sistema responde Y                                    ║
║ 3. Ator confirma Z                                       ║
║ 4. Sistema registra e exibe confirmação                  ║
╠══════════════════════════════════════════════════════════╣
║ FLUXO ALTERNATIVO:                                       ║
║ 2a. Se dados inválidos → Sistema exibe mensagem de erro  ║
╠══════════════════════════════════════════════════════════╣
║ FLUXO DE EXCEÇÃO:                                        ║
║ *. Sistema indisponível → Exibir mensagem de manutenção  ║
╚══════════════════════════════════════════════════════════╝
```


#### Exemplo: Sistema de Biblioteca

**UC-001: Emprestar Livro**

| Campo | Descrição |
|-------|-----------|
| **ID** | UC-001 |
| **Ator Principal** | Bibliotecário |

| **Pré-condição** | Bibliotecário autenticado no sistema; Aluno cadastrado |
| **Pós-condição** | Livro registrado como emprestado; Data de devolução definida |

### 3. Diagrama de Classes UML

O Diagrama de Classes é o mais utilizado na UML. Representa a **estrutura estática** do sistema: classes, atributos, métodos e relacionamentos.

#### Notação de Visibilidade

| Símbolo | Visibilidade | Significado |
|:-------:|:------------|:-----------|
| `+` | public | Acessível por qualquer classe |
| `-` | private | Acessível apenas pela própria classe |
| `#` | protected | Acessível pela classe e suas subclasses |
| `~` | package | Acessível no mesmo pacote |

#### Tipos de Relacionamentos

| Relação | Símbolo | Descrição |
|---------|:-------:|-----------|
| Associação | `———` | Relação simples entre classes |
| Herança | `——▷` | "É um tipo de" (generalização) |
| Composição | `——◆` | "É parte de" (forte — parte não existe sem o todo) |
| Agregação | `——◇` | "Tem um" (fraca — parte existe independente) |
| Dependência | `- - ▶` | Uso temporário |

### 4. Padrões de Projeto (Design Patterns)

Os Padrões de Projeto são soluções reutilizáveis para problemas recorrentes no design de software. Foram catalogados pelo "Gang of Four" (GoF) em 1994.

#### Categorias

| Categoria | Objetivo | Exemplos |
|-----------|----------|----------|
| **Criacionais** | Controlam a criação de objetos | Singleton, Factory Method, Abstract Factory, Builder |
| **Estruturais** | Organizam a composição de classes/objetos | Adapter, Decorator, Facade, Composite |
| **Comportamentais** | Gerenciam comunicação entre objetos | Observer, Strategy, Command, State |

#### Singleton (Criacional)

**Problema**: Garantir que uma classe tenha apenas **uma instância** e fornecer um ponto global de acesso.

**Quando usar**: Conexão com banco de dados, gerenciador de configurações, logger.

```python
class DatabaseConnection:
    """
    Padrão Singleton: Garante apenas uma instância de conexão com o banco.
    """
    _instance = None
    
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._connection = None
        return cls._instance
    
    def connect(self, host: str, database: str):
        """Conecta ao banco de dados (simula conexão)."""
        if self._connection is None:
            self._connection = f"Conectado a {database}@{host}"
            print(f"✅ Nova conexão: {self._connection}")
        else:
            print(f"♻️ Reutilizando conexão existente: {self._connection}")
        return self._connection
    
    def disconnect(self):
        """Encerra a conexão."""
        self._connection = None
        print("❌ Conexão encerrada")


# --- Uso do Singleton ---
db1 = DatabaseConnection()
db2 = DatabaseConnection()

db1.connect("localhost", "escola_db")
db2.connect("localhost", "escola_db")  # Reutiliza a mesma conexão

print(f"\ndb1 é db2? {db1 is db2}")  # True — mesma instância!
```

**Saída esperada:**
```
✅ Nova conexão: Conectado a escola_db@localhost
♻️ Reutilizando conexão existente: Conectado a escola_db@localhost

db1 é db2? True
```

#### Factory Method (Criacional)

**Problema**: Criar objetos sem especificar a classe exata, delegando a decisão para subclasses.

**Quando usar**: Sistema de notificações (email, SMS, push), criação de documentos em diferentes formatos.

```python
from abc import ABC, abstractmethod


# --- Interface (Produto) ---
class Notificacao(ABC):
    """Classe abstrata que define o contrato para notificações."""
    
    @abstractmethod
    def enviar(self, destinatario: str, mensagem: str) -> str:
        pass


# --- Produtos Concretos ---
class NotificacaoEmail(Notificacao):
    def enviar(self, destinatario: str, mensagem: str) -> str:
        return f"📧 Email para {destinatario}: {mensagem}"


class NotificacaoSMS(Notificacao):
    def enviar(self, destinatario: str, mensagem: str) -> str:
        return f"📱 SMS para {destinatario}: {mensagem}"


class NotificacaoPush(Notificacao):
    def enviar(self, destinatario: str, mensagem: str) -> str:
        return f"🔔 Push para {destinatario}: {mensagem}"


# --- Factory (Criador) ---
class NotificacaoFactory:
    """
    Factory Method: Cria a notificação correta baseada no tipo.
    Vantagem: Adicionar novos tipos não altera o código existente (Open/Closed).
    """
    
    @staticmethod
    def criar(tipo: str) -> Notificacao:
        fabricas = {
            "email": NotificacaoEmail,
            "sms": NotificacaoSMS,
            "push": NotificacaoPush
        }
        
        if tipo not in fabricas:
            raise ValueError(f"Tipo '{tipo}' não suportado. Use: {list(fabricas.keys())}")
        
        return fabricas[tipo]()


# --- Uso da Factory ---
factory = NotificacaoFactory()

# Criar diferentes tipos de notificação sem conhecer as classes concretas
notif1 = factory.criar("email")
notif2 = factory.criar("sms")
notif3 = factory.criar("push")

print(notif1.enviar("aluno@escola.com", "Sua nota foi lançada!"))
print(notif2.enviar("81999998888", "Prova amanhã às 14h"))
print(notif3.enviar("user_123", "Novo material disponível"))
```

**Saída esperada:**
```
📧 Email para aluno@escola.com: Sua nota foi lançada!
📱 SMS para 81999998888: Prova amanhã às 14h
🔔 Push para user_123: Novo material disponível
```

> 💡 **Princípio SOLID aplicado**: O Factory Method respeita o **Open/Closed Principle** — o sistema está aberto para extensão (novos tipos de notificação) mas fechado para modificação.

### 5. Tipos de Testes de Software

#### Tabela Comparativa

| Critério | Caixa-Preta | Caixa-Branca | Integração | Sistema |
|----------|:-----------:|:------------:|:----------:|:-------:|
| **Foco** | Funcionalidade (entradas/saídas) | Estrutura interna (código) | Comunicação entre módulos | Sistema completo |
| **Conhecimento do código** | ❌ Não necessário | ✅ Necessário | Parcial | ❌ Não necessário |
| **Quem executa** | Testador/QA | Desenvolvedor | Desenvolvedor/QA | QA/Usuário |
| **Quando** | Após desenvolvimento | Durante desenvolvimento | Após testes unitários | Antes da entrega |
| **Técnicas** | Partição de equivalência, Valor limite | Cobertura de caminhos, Condições | Top-down, Bottom-up, Big-bang | Funcional, Performance, Segurança |
| **Exemplo** | Testar login com dados válidos/inválidos | Verificar se todos os `if/else` são percorridos | Testar se módulo de pagamento comunica com estoque | Testar fluxo completo de compra |
| **Nível** | Funcional | Estrutural | Intermediário | Alto nível |


### A4 — Implementar Singleton + Factory em Python 🔴 Desafiador

**Objetivo**: Combinar dois padrões de projeto em uma solução prática.

**Enunciado**: Implemente um sistema de **Logger** que:
1. Use o padrão **Singleton** para garantir uma única instância do gerenciador de logs
2. Use o padrão **Factory** para criar diferentes tipos de log (Console, Arquivo, Banco de Dados)
3. Cada log deve ter um método `registrar(mensagem, nivel)` onde nível pode ser: INFO, WARNING, ERROR
4. Inclua timestamp em cada registro

<details>
<summary>📋 Ver Resposta</summary>

```python
from abc import ABC, abstractmethod
from datetime import datetime


# ========================================
# FACTORY: Diferentes tipos de Logger
# ========================================

class Logger(ABC):
    """Interface para todos os tipos de logger."""
    
    @abstractmethod
    def registrar(self, mensagem: str, nivel: str) -> str:
        pass
    
    def _formatar(self, mensagem: str, nivel: str) -> str:
        """Formato padrão: [TIMESTAMP] [NIVEL] mensagem"""
        timestamp = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
        return f"[{timestamp}] [{nivel.upper()}] {mensagem}"


class LoggerConsole(Logger):
    """Exibe logs no terminal."""
    
    def registrar(self, mensagem: str, nivel: str) -> str:
        icones = {"INFO": "ℹ️", "WARNING": "⚠️", "ERROR": "❌"}
        icone = icones.get(nivel.upper(), "📝")
        log = f"{icone} {self._formatar(mensagem, nivel)}"
        print(log)
        return log


class LoggerArquivo(Logger):
    """Salva logs em arquivo de texto."""
    
    def __init__(self, arquivo: str = "app.log"):
        self.arquivo = arquivo
    
    def registrar(self, mensagem: str, nivel: str) -> str:
        log = self._formatar(mensagem, nivel)
        # Em produção: open(self.arquivo, 'a') e escreve
        resultado = f"📄 [{self.arquivo}] {log}"
        print(resultado)
        return resultado


class LoggerBancoDados(Logger):
    """Registra logs no banco de dados."""
    
    def registrar(self, mensagem: str, nivel: str) -> str:
        log = self._formatar(mensagem, nivel)
        # Em produção: INSERT INTO logs (timestamp, nivel, mensagem) VALUES (...)
        resultado = f"🗄️ [DB] {log}"
        print(resultado)
        return resultado


class LoggerFactory:
    """Factory Method: Cria o logger adequado."""
    
    @staticmethod
    def criar(tipo: str, **kwargs) -> Logger:
        loggers = {
            "console": LoggerConsole,
            "arquivo": LoggerArquivo,
            "banco": LoggerBancoDados
        }
        if tipo not in loggers:
            raise ValueError(f"Tipo '{tipo}' inválido. Opções: {list(loggers.keys())}")
        return loggers[tipo](**kwargs)


# ========================================
# SINGLETON: Gerenciador único de Logs
# ========================================

class GerenciadorLogs:
    """
    Singleton + Factory combinados.
    Gerencia múltiplos loggers e garante instância única.
    """
    _instance = None
    
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._loggers = []
        return cls._instance
    
    def adicionar_logger(self, tipo: str, **kwargs):
        """Adiciona um novo canal de log via Factory."""
        logger = LoggerFactory.criar(tipo, **kwargs)
        self._loggers.append(logger)
        print(f"✅ Logger '{tipo}' adicionado ao gerenciador")
    
    def info(self, mensagem: str):
        """Registra mensagem INFO em todos os loggers."""
        for logger in self._loggers:
            logger.registrar(mensagem, "INFO")
    
    def warning(self, mensagem: str):
        """Registra mensagem WARNING em todos os loggers."""
        for logger in self._loggers:
            logger.registrar(mensagem, "WARNING")
    
    def error(self, mensagem: str):
        """Registra mensagem ERROR em todos os loggers."""
        for logger in self._loggers:
            logger.registrar(mensagem, "ERROR")


# ========================================
# USO COMBINADO
# ========================================

# Criando o gerenciador (Singleton)
gerenciador = GerenciadorLogs()
gerenciador.adicionar_logger("console")
gerenciador.adicionar_logger("arquivo", arquivo="sistema.log")

# Testando Singleton: mesma instância
outro_gerenciador = GerenciadorLogs()
print(f"\nMesma instância? {gerenciador is outro_gerenciador}")  # True
print(f"Loggers configurados: {len(outro_gerenciador._loggers)}")  # 2

# Registrando logs
print("\n--- Registrando eventos ---")
gerenciador.info("Sistema iniciado com sucesso")
gerenciador.warning("Uso de memória acima de 80%")
gerenciador.error("Falha na conexão com servidor externo")
```

**7.** Implemente em Python o padrão **Observer** para um sistema de notificação onde um `Canal` (subject) notifica `Inscritos` (observers) quando um novo vídeo é publicado.

<details>
<summary>Ver Resposta</summary>

```python
from abc import ABC, abstractmethod


class Observer(ABC):
    """Interface Observer — quem recebe notificações."""
    
    @abstractmethod
    def atualizar(self, canal: str, video: str):
        pass


class Inscrito(Observer):
    """Observer concreto — um inscrito do canal."""
    
    def __init__(self, nome: str):
        self.nome = nome
    
    def atualizar(self, canal: str, video: str):
        print(f"🔔 {self.nome} recebeu: '{canal}' publicou '{video}'")


class Canal:
    """Subject — o canal que notifica inscritos."""
    
    def __init__(self, nome: str):
        self.nome = nome
        self._inscritos: list[Observer] = []
        self._videos: list[str] = []
    
    def inscrever(self, inscrito: Observer):
        self._inscritos.append(inscrito)
        print(f"✅ {inscrito.nome} se inscreveu em '{self.nome}'")
    
    def desinscrever(self, inscrito: Observer):
        self._inscritos.remove(inscrito)
        print(f"❌ {inscrito.nome} saiu de '{self.nome}'")
    
    def publicar_video(self, titulo: str):
        """Publica vídeo e notifica TODOS os inscritos."""
        self._videos.append(titulo)
        print(f"\n📹 '{self.nome}' publicou: '{titulo}'")
        self._notificar(titulo)
    
    def _notificar(self, video: str):
        """Notifica cada observer registrado."""
        for inscrito in self._inscritos:
            inscrito.atualizar(self.nome, video)


# --- Uso ---
canal = Canal("Python Brasil")

ana = Inscrito("Ana")
pedro = Inscrito("Pedro")
maria = Inscrito("Maria")

canal.inscrever(ana)
canal.inscrever(pedro)
canal.inscrever(maria)

canal.publicar_video("Padrões de Projeto em Python")
canal.desinscrever(pedro)
canal.publicar_video("Clean Code na Prática")
```

**3.** Em UML, o relacionamento de **composição** entre classes significa:

- a) Uma classe usa temporariamente outra
- b) Uma classe é um tipo especializado de outra
- c) Uma parte não pode existir sem o todo (dependência forte)
- d) Uma parte pode existir independente do todo (dependência fraca)

<details>
<summary>Ver Resposta</summary>

**Resposta: c)**

**Composição** (losango preenchido ◆): relação "parte-de" forte. Se o todo for destruído, as partes também são.

Exemplo: `Pedido ◆── ItemPedido` — se o pedido é deletado, seus itens deixam de existir.

**Agregação** (losango vazio ◇): relação "tem-um" fraca. As partes existem independentemente.

Exemplo: `Universidade ◇── Professor` — se a universidade fechar, o professor continua existindo.

</details>

**5.** Em testes de software, a técnica de **Partição de Equivalência** consiste em:

- a) Testar todos os valores possíveis de entrada
- b) Dividir as entradas em grupos que devem ter o mesmo comportamento
- c) Testar apenas os valores nos limites do domínio
- d) Verificar todos os caminhos internos do código

<details>
<summary>Ver Resposta</summary>

**Resposta: b)**

A **Partição de Equivalência** divide o domínio de entrada em classes onde todos os valores de uma mesma classe devem produzir o mesmo resultado.

Exemplo: Para um campo "idade" (válido: 18-65):
- Classe válida: 18 ≤ idade ≤ 65 → testar com 30 (representante)
- Classe inválida 1: idade < 18 → testar com 10
- Classe inválida 2: idade > 65 → testar com 80

Não é necessário testar 18, 19, 20... 64, 65 — basta um representante de cada classe.

</details>

| **Semanas** | 2-3 |

**Roteiro da Professora:**
1. [5 min] Dividir turma em squads (4-5 alunos) — atribuir papéis (PO, SM, Devs)
2. [10 min] PO apresenta Product Backlog (post-its no quadro com User Stories)
3. [15 min] Equipe seleciona itens para o Sprint (mover post-its para Sprint Backlog)
4. [15 min] Equipe quebra histórias em tarefas técnicas (sub-post-its)
5. [5 min] Cada squad apresenta seu Sprint Backlog (30 seg cada)

**Guia do Aluno:**
> 🎯 Vocês são um time Scrum REAL! O PO do grupo vai apresentar o backlog. Juntos, decidam o que cabe no Sprint de 2 semanas. Escrevam cada tarefa em um post-it.

#### Atividade B2 — "Diagrama UML no Quadro" 🟡

| Item | Detalhe |
|------|---------|
| **Objetivo** | Construir coletivamente um diagrama de classes UML |
| **Materiais** | Quadro branco, marcadores coloridos (3 cores: classe, atributo, relação) |
| **Duração** | 40 minutos |
| **Semanas** | 7-9 |

**Roteiro da Professora:**
1. [5 min] Apresentar o sistema a ser modelado (ex: "Sistema de Biblioteca")
2. [10 min] Brainstorm coletivo: "Que CLASSES precisamos?" (anotar no quadro)
3. [15 min] Alunos vão ao quadro em turnos — cada um adiciona 1 atributo ou 1 método
4. [10 min] Desenhar relacionamentos (herança, composição, associação) coletivamente

**Guia do Aluno:**
> 🎯 Cada um vai ao quadro UMA VEZ para adicionar algo ao diagrama. Pode ser: uma classe, um atributo, um método ou um relacionamento. Pense antes de ir!

---

#### Atividade B3 — "Planning Poker Humano" 🟢

| Item | Detalhe |
|------|---------|
| **Objetivo** | Praticar estimativa ágil com técnica de Planning Poker |
| **Materiais** | Cartões numerados (1, 2, 3, 5, 8, 13, 21) — 1 jogo por aluno |
| **Duração** | 30 minutos |
| **Semanas** | 2-4 |

**Roteiro da Professora:**
1. [5 min] Distribuir cartões e explicar a escala Fibonacci
2. [5 min] Apresentar 1ª User Story — turma estima simultaneamente (levanta cartão)
3. [5 min] Quem deu o MAIOR e o MENOR explica seu raciocínio
4. [15 min] Repetir para mais 3-4 histórias
5. Consenso: re-votar até convergir

**Guia do Aluno:**
> 🎯 Quando a professora ler a User Story, escolha o cartão que representa sua estimativa de esforço. Levante junto com todos! Se seu número for muito diferente dos outros, explique por quê.

---

#### Atividade B4 — "Kanban Físico" 🟢

| Item | Detalhe |
|------|---------|
| **Objetivo** | Gerenciar fluxo de trabalho visual com quadro Kanban |
| **Materiais** | Quadro branco dividido em 3 colunas, post-its |
| **Duração** | Uso contínuo (durante toda a aula) |
| **Semanas** | 1-4 |

**Roteiro da Professora:**
1. Dividir quadro em: `📋 TO DO` | `🔨 DOING` | `✅ DONE`
2. No início da aula, colocar tarefas do dia em "To Do"
3. Conforme turma executa, alunos movem post-its
4. No final da aula, revisar: "O que ficou em DOING? Por quê?"

---

#### Atividade B5 — "Retrospectiva em Sala" 🟡

| Item | Detalhe |
|------|---------|
| **Objetivo** | Vivenciar uma Sprint Retrospective real do Scrum |
| **Materiais** | 3 cartazes: "😊 O que deu certo?", "😤 O que melhorar?", "🎯 Ações!" |
| **Duração** | 25 minutos |
| **Semanas** | 4, 10, 20 (final de cada bloco) |

**Roteiro da Professora:**
1. [5 min] Colar 3 cartazes na parede — distribuir post-its
2. [10 min] Alunos escrevem e colam (anônimo se preferirem)
3. [5 min] Ler em voz alta e agrupar temas semelhantes
4. [5 min] Votar nas 2 ações mais importantes para o próximo bloco

**Guia do Aluno:**
> 🎯 Isso é uma Retrospectiva REAL — equipes ágeis fazem isso toda Sprint! Seja honesto(a): o que funcionou na aula? O que atrapalhou? O que podemos mudar?

### 💼 Opção C: Estudo de Caso / PBL (Problem-Based Learning)

> 💡 **Conceito:** Aprender Engenharia de Software analisando falhas reais e modelos de sucesso da indústria.

#### Caso 1 — "O Fracasso do Healthcare.gov" (Falta de Engenharia de Software)

| Item | Detalhe |
|------|---------|
| **Tema** | O portal de saúde dos EUA custou $2 bilhões e falhou no lançamento em 2013 |
| **Conexão** | Requisitos mal definidos, falta de testes, gerenciamento de projeto caótico |
| **Duração** | 50 minutos |
| **Formato** | Narrativa + análise de falhas + propostas |

**Roteiro:**
1. [15 min] Professora narra o caso: 55 fornecedores, nenhum dono do produto, zero testes integrados
2. [15 min] Turma em grupos: "Que práticas de Eng. Software teriam evitado o desastre?"
3. [15 min] Cada grupo apresenta 3 práticas (Scrum? Testes? Arquitetura? Requisitos?)
4. [5 min] Síntese: relação com conteúdo da disciplina

---

#### Caso 2 — "Como o Spotify Organiza Squads" (Agile at Scale)

| Item | Detalhe |
|------|---------|
| **Tema** | Modelo Spotify: Squads, Tribes, Chapters, Guilds |
| **Conexão** | Scrum, metodologias ágeis, organização de equipes |
| **Duração** | 50 minutos |
| **Formato** | Vídeo/texto + mapeamento + proposta de organização |

**Roteiro:**
1. [10 min] Apresentar o modelo Spotify (diagrama no quadro)
2. [15 min] Debate: "Que problemas esse modelo resolve? Quais cria?"
3. [20 min] Exercício: "Se nossa turma fosse uma Tribe, como dividir em Squads?"
4. [5 min] Reflexão: autonomia vs. alinhamento

---

#### Caso 3 — "Boeing 737 MAX — Falha de Requisitos" (Consequências)

| Item | Detalhe |
|------|---------|
| **Tema** | Software MCAS com requisitos incompletos causou 346 mortes |
| **Conexão** | Requisitos não-funcionais, testes, ética em software, ciclo de vida |
| **Duração** | 50 minutos |
| **Formato** | Narrativa + debate ético + lições aprendidas |

**Roteiro:**
1. [15 min] Professora narra: sensor único, treinamento omitido, pressão de mercado
2. [15 min] Debate ético: "Desenvolvedores têm responsabilidade em acidentes causados por software?"
3. [15 min] Turma redige coletivamente: "5 lições da Boeing para engenheiros de software"
4. [5 min] Conexão com a disciplina: Requisitos Não-Funcionais de segurança
