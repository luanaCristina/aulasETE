## 📖 Sobre a Disciplina

O Projeto Integrador III é o **projeto capstone** (projeto de conclusão) do curso técnico. As equipes desenvolverão uma **solução completa** — do design à implementação — integrando TODAS as competências adquiridas nos 3 módulos:

- 📱 **Mobile** — App Android nativo (Kotlin)
- ☁️ **Cloud** — Backend Firebase (Firestore, Auth, Storage, Functions)
- 🎨 **Design** — Interface projetada no Figma seguindo guidelines
- 🔒 **Segurança** — Conformidade LGPD, autenticação, regras de segurança
- 📐 **Engenharia** — Scrum, documentação, qualidade

> **100% baseado em projeto** — Não há provas teóricas. A avaliação é contínua e baseada em entregas incrementais (sprints).

## 🎯 Objetivos

### Objetivo Geral
Desenvolver uma solução mobile completa, do conceito ao produto funcional, integrando design, desenvolvimento, cloud computing e segurança da informação em um projeto capstone profissional.

### Objetivos Específicos
- Planejar e executar um projeto de software usando Scrum
- Projetar interfaces mobile profissionais (Figma + Material Design)
- Desenvolver app Android nativo com Kotlin
- Integrar backend Firebase (Auth, Firestore, Storage, Functions)
- Garantir conformidade com LGPD (dados pessoais, consentimento)
- Apresentar e defender o projeto em Demo Day com banca avaliadora
- Trabalhar em equipe com papéis definidos e retrospectivas

## 🔄 Metodologia Scrum

### Papéis da Equipe (3-5 membros)

| Papel | Responsabilidade |
|-------|-----------------|
| **Product Owner (PO)** | Define prioridades, aceita entregas, voz do cliente |
| **Scrum Master** | Facilita cerimônias, remove impedimentos, garante processo |
| **Dev Mobile** | Desenvolve o app Android (Kotlin) |
| **Dev Backend/Cloud** | Configura Firebase, Cloud Functions, regras |
| **Designer** | Cria interface no Figma, faz testes de usabilidade |

> **Nota:** Em equipes de 3, membros acumulam papéis. Todos devem contribuir com código.

### Cerimônias Scrum

| Cerimônia | Frequência | Duração | Descrição |
|-----------|-----------|---------|-----------|
| Sprint Planning | Início de cada sprint | 30min | Planejar tarefas da sprint |
| Daily Standup | 2x por semana (em aula) | 5min | O que fiz, o que vou fazer, impedimentos |
| Sprint Review | Final de cada sprint | 20min | Demo para a professora |
| Sprint Retrospective | Final de cada sprint | 15min | O que melhorar no processo |

### Ferramentas de Gestão

| Ferramenta | Uso |
|-----------|-----|
| GitHub Projects (Kanban) | Backlog, To Do, In Progress, Done |
| GitHub Issues | Tasks e bugs |
| Google Docs | Documentação |
| Figma | Design e protótipos |
| Firebase Console | Backend e monitoramento |

## 💡 Temas Sugeridos

### Categoria: Saúde e Bem-estar
- **MedAlerta** — App de lembretes de medicamentos para idosos (com notificações push)
- **SaúdeLocal** — Localizar UBS, farmácias e agendar consultas pelo SUS
- **FitTracker** — Registro de atividades físicas com metas e progresso

### Categoria: Serviço Comunitário
- **Vizinho Solidário** — Rede de ajuda entre vizinhos (doações, serviços, eventos)
- **Adote.PE** — Plataforma de adoção de animais em Pernambuco
- **Alerta Cidadão** — Reportar problemas urbanos (buracos, lixo, poste apagado)

### Categoria: Comércio Local
- **FeiraPE** — Marketplace de feirantes e produtores locais
- **DeskFácil** — Agendamento para serviços locais (barbearia, manicure, etc.)
- **Cantina Digital** — Sistema de pedidos e saldo para cantina escolar

### Categoria: Educação
- **EstudaJunto** — App de grupos de estudo + flashcards compartilhados
- **BibliON** — Gestão de biblioteca escolar com empréstimos digitais
- **NotaFácil** — Acompanhamento de notas e frequência para pais/alunos

### Regras de Escolha de Tema
- ✅ Resolver um problema REAL (da comunidade, escola ou público)
- ✅ Ter usuários reais que possam testar o app
- ✅ Ser viável em 20 semanas com equipe de 3-5 alunos
- ❌ Não pode ser clone exato de app existente
- ❌ Não pode ser apenas CRUD básico sem diferencial

## ✅ Requisitos Mínimos

### Checklist Obrigatório

#### Design (Sprint 1)
- [ ] Wireframes de todas as telas no Figma
- [ ] Design System com tokens (cores, fonts, spacing)
- [ ] Protótipo interativo testável no Figma Mirror
- [ ] Seguir Material Design 3 guidelines

#### Backend Cloud (Sprint 2)
- [ ] Firebase Authentication (email/senha OU Google Sign-In)
- [ ] Firestore com pelo menos 3 coleções
- [ ] Firebase Storage para upload de pelo menos 1 tipo de arquivo
- [ ] Pelo menos 1 Cloud Function (trigger ou HTTP)
- [ ] Security Rules configuradas (não pode ter `allow: true`)

#### Frontend Mobile (Sprint 3)
- [ ] App Android nativo em Kotlin
- [ ] Mínimo 5 telas funcionais
- [ ] RecyclerView com dados do Firestore
- [ ] Navegação (Navigation Component ou similar)
- [ ] Formulários com validação
- [ ] Tratamento de erros (sem crashes)

#### Segurança e LGPD (Sprint 4)
- [ ] Tela de consentimento/aceite de política
- [ ] Política de Privacidade acessível no app
- [ ] Dados sensíveis criptografados
- [ ] Opção de excluir conta/dados (direito do titular)
- [ ] Sem dados desnecessários coletados (minimização)

#### Documentação (Fase Final)
- [ ] README.md completo no GitHub
- [ ] Manual do usuário (1-2 páginas)
- [ ] Documentação técnica (arquitetura, banco, APIs)
- [ ] Vídeo demonstrativo (2-3 minutos)

## 📊 Rubrica de Avaliação

### Avaliação Geral (100%)

| Componente | Peso | Detalhamento |
|-----------|------|--------------|
| Sprint 1 — Design | 15% | Wireframes, design system, protótipo |
| Sprint 2 — Backend | 20% | Firebase config, auth, rules, functions |
| Sprint 3 — Mobile | 25% | App funcional, integração, UX |
| Sprint 4 — Security | 10% | LGPD, testes, polish |
| Documentação | 10% | README, manual, docs técnicos |
| Demo Day | 15% | Pitch + demo + respostas |
| Processo (Scrum) | 5% | Participação, atas, Kanban atualizado |

### Rubrica Detalhada por Nota

| Nota | Descrição |
|------|-----------|
| **10** | App completo, polido, sem bugs, demo excelente, documentação impecável |
| **8-9** | App funcional com pequenos problemas, boa apresentação, docs completos |
| **6-7** | App funciona parcialmente, design ou backend incompleto, apresentação ok |
| **4-5** | App com bugs críticos, faltam funcionalidades obrigatórias |
| **< 4** | Projeto muito incompleto ou não apresentado no Demo Day |

### Critérios por Sprint (detalhado)

#### Sprint 1 — Design (15%)
| Sub-critério | 0-2 | 3-4 | 5 |
|-------------|-----|-----|---|
| Wireframes | Incompletos | Todas as telas, mas básico | Completo + flows |
| Design System | Sem tokens | Tokens parciais | Completo (cor, tipo, spacing) |
| Protótipo | Não funcional | Navegação básica | Interativo com animações |
| Guidelines | Não segue | Parcialmente | MD3/HIG corretamente |

#### Sprint 2 — Backend (20%)
| Sub-critério | 0-2 | 3-4 | 5 |
|-------------|-----|-----|---|
| Authentication | Não funciona | Email/senha básico | + Social login + recovery |
| Firestore | 1-2 coleções | 3 coleções com queries | + subcoleções + índices |
| Cloud Functions | Nenhuma | 1 function simples | 2+ functions complexas |
| Security Rules | `allow: true` | Regras básicas | Regras completas + validação |

#### Sprint 3 — Mobile (25%)
| Sub-critério | 0-2 | 3-4 | 5 |
|-------------|-----|-----|---|
| Telas | < 3 telas | 5 telas funcionais | 7+ telas polidas |
| Integração | Parcial | CRUD completo | + Offline + Real-time |
| UX | Confuso, lento | Funcional | Fluido, intuitivo, animado |
| Código | Desorganizado | Organizado | Clean code + padrões |

#### Atividade B1: Sprint Planning Presencial — Kanban no Quadro

| Item | Descrição |
|------|-----------|
| **Tema** | Planejamento de sprint usando Kanban físico |
| **Duração** | 50 minutos |
| **Materiais** | Quadro branco, post-its (3 cores), caneta, fita adesiva |
| **Objetivo** | Planejar a próxima sprint com Kanban físico + Planning Poker manual |

**📋 Roteiro do Professor:**
```
1. (10 min) SETUP DO KANBAN NO QUADRO:
   • Dividir quadro em 4 colunas: Backlog | To Do | In Progress | Done
   • Cada equipe recebe post-its de 3 cores:
     - 🟡 Amarelo = Funcionalidade nova
     - 🔵 Azul = Bug/correção
     - 🟢 Verde = Documentação/design

2. (15 min) PLANNING POKER MANUAL:
   • Cada membro tem "cartas" (folhas com 1, 2, 3, 5, 8, 13)
   • PO apresenta cada item do backlog
   • Todos revelam estimativa ao mesmo tempo
   • Se divergência > 3 pontos → discutir e re-estimar

3. (20 min) SPRINT PLANNING:
   • Equipes selecionam itens do Backlog → To Do
   • Definir responsável (iniciais no post-it)
   • Definir critério de "Done" para cada item
   • Meta da sprint escrita no quadro

4. (5 min) SPRINT GOAL:
   • Cada equipe declara em 1 frase o objetivo da sprint
   • Fotografar o quadro (evidência)
```

**📋 Guia do Aluno — Sprint Planning:**
```
╔══════════════════════════════════════════════════════╗
║  SPRINT PLANNING — KANBAN NO QUADRO                  ║
╠══════════════════════════════════════════════════════╣
║                                                      ║
║  1. Escrever TODAS as tarefas pendentes em post-its  ║
║     (1 tarefa por post-it, letra legível!)           ║
║                                                      ║
║  2. PLANNING POKER:                                  ║
║     • Ouvir a descrição da tarefa                    ║
║     • Escolher sua carta (1=fácil, 13=muito difícil) ║
║     • Revelar ao mesmo tempo que os colegas          ║
║     • Quem deu maior e menor: explicar por quê      ║
║                                                      ║
║  3. Selecionar tarefas para esta sprint              ║
║     (não pegar mais do que consegue entregar!)       ║
║                                                      ║
║  4. Colocar suas iniciais nos post-its que assumiu   ║
║                                                      ║
║  5. Fotografar o quadro final                        ║
╚══════════════════════════════════════════════════════╝
```

#### Atividade B2: Code Review em Papel

| Item | Descrição |
|------|-----------|
| **Tema** | Revisão de código impresso entre duplas |
| **Duração** | 50 minutos |
| **Materiais** | Código impresso (2 páginas por aluno), caneta vermelha, checklist impresso |
| **Objetivo** | Praticar code review como processo de qualidade |

**📋 Roteiro do Professor:**
```
1. (5 min) EXPLICAR CODE REVIEW:
   • Por que fazemos? (bugs, aprendizado, padrões)
   • Regras: ser construtivo, focar no código não na pessoa
   • Checklist: nomes claros? sem repetição? tratou erros?

2. (5 min) DISTRIBUIR MATERIAL:
   • Cada aluno recebe código DIFERENTE do seu colega
   • Caneta vermelha + checklist de review

3. (30 min) REVIEW EM DUPLAS:
   • Ler o código linha por linha
   • Marcar com caneta vermelha:
     ✓ = Bom! Bem feito
     ? = Não entendi, precisa explicação
     ✗ = Problema (bug, nome ruim, falta tratamento de erro)
   • Escrever comentários na margem

4. (10 min) FEEDBACK PRESENCIAL:
   • Duplas conversam sobre os achados
   • Autor explica decisões, revisor sugere melhorias
   • Anotar 3 ações de melhoria (to-do list)
```

**📋 Guia do Aluno — Code Review:**
```
╔══════════════════════════════════════════════════════╗
║  CODE REVIEW EM PAPEL — CHECKLIST                    ║
╠══════════════════════════════════════════════════════╣
║                                                      ║
║  Para cada trecho de código, verificar:              ║
║  □ Nomes de variáveis são descritivos?              ║
║  □ Funções fazem uma coisa só?                      ║
║  □ Tem tratamento de erro (try/catch)?              ║
║  □ Código é legível sem comentários?                ║
║  □ Há código duplicado que poderia ser função?      ║
║  □ Segue padrão do projeto (indentação, estilo)?    ║
║  □ Dados do usuário são validados?                  ║
║  □ Não tem console.log/print esquecido?             ║
║                                                      ║
║  MARCAR COM CANETA VERMELHA:                         ║
║  ✓ = Aprovado (bom código!)                         ║
║  ? = Dúvida (perguntar ao autor)                    ║
║  ✗ = Problema (precisa corrigir)                    ║
║  💡 = Sugestão (melhoria opcional)                   ║
║                                                      ║
║  Ao final: escrever 3 elogios + 3 melhorias         ║

#### Atividade B5: Retrospectiva Ágil com Post-its

| Item | Descrição |
|------|-----------|
| **Tema** | Sprint Retrospective presencial |
| **Duração** | 40 minutos |
| **Materiais** | Post-its (3 cores), quadro dividido em 3 colunas |
| **Objetivo** | Refletir sobre o processo e definir ações de melhoria |

**📋 Roteiro do Professor:**
```
1. (5 min) SETUP DO QUADRO:
   Dividir em 3 colunas:
   😊 O que foi bem | 😐 O que melhorar | 🎯 Ações

2. (10 min) ESCRITA INDIVIDUAL:
   • Cada membro escreve em silêncio (1 item por post-it)
   • Verde = O que foi bem (mínimo 2)
   • Amarelo = O que melhorar (mínimo 2)
   • Não escrever nome (anônimo!)

3. (10 min) COLAGEM + AGRUPAMENTO:
   • Colar post-its no quadro (coluna correta)
   • Agrupar similares (temas que se repetem)
   • Ler em voz alta os agrupamentos

4. (10 min) VOTAÇÃO + AÇÕES:
   • Cada membro vota (com caneta) nos 2 mais importantes
   • Top 3 mais votados → definir AÇÃO concreta
   • Ação: quem faz? até quando?

5. (5 min) REGISTRO:
   • Fotografar quadro (evidência)
   • 1 aluno registra ata com as 3 ações definidas
```

╠══════════════════════════════════════════════════════╣
║                                                      ║
║  CONTEXTO:                                           ║
║  Equipe de 5 alunos, projeto integrador 2025.       ║

║  Tinham 20 semanas. Resultado: app não funcionou    ║
║  no Demo Day. Nota: 3.5                             ║

║  O QUE ACONTECEU (timeline):                        ║
║  • Semanas 1-6: debateram o tema, sem código        ║

║  • Semanas 8-12: 2 devs fizeram tudo, 2 sumiram    ║

║  • Semana 18: tentaram integrar tudo → conflitos    ║
║  • Semana 20: Demo Day → app crashou ao vivo       ║
║                                                      ║
║  EVIDÊNCIAS:                                        ║
║  • GitHub: 80% dos commits de 1 pessoa              ║
║  • Kanban: cards nunca movidos após semana 3        ║
║  • Nenhuma Sprint Retrospective registrada          ║
║  • Design no Figma: apenas 2 telas (low-fi)        ║
║                                                      ║
╠══════════════════════════════════════════════════════╣
║  DISCUSSÃO (em grupo):                              ║
║  1. Quais foram as 3 CAUSAS RAIZ do fracasso?       ║
║  2. Em qual semana o projeto "morreu"? Por quê?     ║
║  3. O que o Scrum Master deveria ter feito?         ║
║  4. Como a professora poderia ter intervido antes?  ║
║  5. Reescreva o cronograma: o que fariam diferente? ║
╚══════════════════════════════════════════════════════╝
```

**📋 Roteiro do Professor — Caso 1:**
```
1. (10 min) Apresentar o caso (ler juntos ou projetar)
2. (20 min) Discussão em grupos de 4-5 alunos
3. (15 min) Cada grupo apresenta suas conclusões (3 min cada)
4. (5 min) Síntese: "Lições que aplicaremos no NOSSO projeto"

PERGUNTAS PROVOCATIVAS:
• "Se vocês estivessem nessa equipe, em qual semana teriam
   percebido o problema?"
• "O que é pior: app feio que funciona ou app bonito que crasha?"
• "Como evitar que 1 pessoa faça 80% do trabalho?"
```
