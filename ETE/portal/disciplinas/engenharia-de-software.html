🔍 O que é Engenharia de Software?

É a aplicação de princípios de engenharia ao desenvolvimento de software — planejamento, processo, qualidade e entrega previsível.

🎯 Por que precisamos?

  • Software cresce em complexidade (milhões de linhas)
  • Equipes distribuídas precisam de processo
  • Bugs em produção custam 100x mais que em desenvolvimento
  • Prazo e orçamento precisam ser previsíveis

📊 Pilares da ES

  • Processo: Como organizamos o trabalho
  • Método: Técnicas para análise e design
  • Ferramenta: Suporte automatizado
  • Qualidade: Métricas e testes
💡 Analogia: Construir software sem ES é como construir um prédio sem planta — pode até ficar em pé, mas vai custar caro e cair rápido.

🏃 Scrum — Framework Ágil

👥 Papéis

  • Product Owner: Define O QUE construir (prioriza backlog)
  • Scrum Master: Remove impedimentos, facilita cerimônias
  • Dev Team: Define COMO construir (auto-organizado)

📅 Cerimônias

  • Sprint Planning: O que entra na sprint?
  • Daily Standup: 15min — O que fiz/farei/impedimentos
  • Sprint Review: Demo para stakeholders
  • Retrospectiva: O que melhorar?

📦 Artefatos

  • Product Backlog: Lista priorizada de features
  • Sprint Backlog: Itens selecionados para a sprint
  • Incremento: Software funcional entregue
  • Definition of Done: Critérios de "pronto"
⚠️ Sprint = time-box! Duração fixa (1-4 semanas). Se não terminou, volta pro backlog — NÃO estica o prazo.

📋 Requisitos e User Stories

Formato de User Story

Template COMO [persona/papel do usuário] QUERO [ação/funcionalidade] PARA [benefício/valor de negócio] --- Critérios de Aceite --- ✅ DADO que [contexto] QUANDO [ação] ENTÃO [resultado esperado]

Exemplo Real

User Story COMO paciente QUERO agendar consulta pelo app PARA não precisar ligar para o consultório ✅ DADO que há horários disponíveis QUANDO seleciono médico + data + horário ENTÃO recebo confirmação por push

INVEST — Qualidade da Story

LetraSignificado
IIndependente (sem dependências)
NNegociável (não é contrato)
VValiosa (entrega valor ao usuário)
EEstimável (equipe consegue pontuar)
SSmall (cabe em 1 sprint)
TTestável (tem critérios de aceite)
💡 Se a story não tem critério de aceite, ela não está "pronta para desenvolvimento".

📐 UML — Diagramas Essenciais

📊 Caso de Uso

Mostra: O que o sistema FAZ (visão do usuário)

  • Atores (stick figures)
  • Casos de uso (elipses)
  • Relacionamentos (include, extend)

📍 Fase: Requisitos

🏗️ Diagrama de Classes

Mostra: ESTRUTURA do sistema (dados + relações)

  • Classes (atributos + métodos)
  • Associações (1:1, 1:N, N:M)
  • Herança e composição

📍 Fase: Design

🔄 Diagrama de Sequência

Mostra: COMO objetos se comunicam no tempo

  • Objetos (lifelines)
  • Mensagens (setas)
  • Ordem temporal (top→bottom)

📍 Fase: Design detalhado

🛠️ Ferramentas gratuitas: draw.io (diagramas), PlantUML (texto→diagrama), Mermaid.js (Markdown→diagrama).

🌿 Git e Versionamento

Controle de versão é a espinha dorsal do desenvolvimento em equipe.

Comandos Essenciais

Bash # Configuração inicial git config --global user.name "Seu Nome" git config --global user.email "email@email.com" # Fluxo básico git init git add . git commit -m "feat: tela de login" git push origin main # Branches (trabalho em equipe) git checkout -b feature/cadastro git commit -m "feat: formulário de cadastro" git push origin feature/cadastro # → Abrir Pull Request no GitHub

⚠️ NUNCA faça commit direto na main! Sempre crie uma branch → faça PR → peça code review.

🧪 Qualidade de Software e Testes

Pirâmide de Testes

NívelO que testaVelocidadeQuantidade
UnitárioFunção isolada⚡ RápidoMuitos (70%)
IntegraçãoMódulos juntos🔄 MédioAlguns (20%)
E2ESistema completo🐢 LentoPoucos (10%)
💡 Cada bug encontrado em produção custa 100x mais do que se fosse encontrado na fase de testes.

Tipos de Teste

  • Funcional: O sistema faz o que deveria?
  • Usabilidade: É fácil de usar?
  • Performance: É rápido sob carga?
  • Segurança: Está protegido?
  • Regressão: Nada que funcionava quebrou?

Caso de Teste (Template)

Markdown **CT-01:** Login com credenciais válidas **Pré-condição:** Usuário cadastrado **Passos:** 1. Acessar /login 2. Digitar email e senha 3. Clicar "Entrar" **Resultado esperado:** Redireciona para /dashboard

🚀 Projeto Final — Sprint Simulation

📦 O Projeto

Equipes de 4-5 alunos simulam 2 sprints completas de um sistema real:

  • Definir papéis (PO, SM, Devs)
  • Criar Product Backlog (15+ stories)
  • Sprint Planning (selecionar stories)
  • Daily Standups (registrar em ata)
  • Sprint Review (demo funcional)
  • Retrospectiva (melhorias)

📄 Entregáveis

  • Product Backlog priorizado no GitHub Projects
  • Diagrama de Caso de Uso (draw.io)
  • Diagrama de Classes
  • Repositório Git com branches e PRs
  • Plano de Testes (5+ casos)
  • Apresentação Sprint Review (10 min)
💡 Sugestão de tema: AgendaPro (sistema de agendamento), e-commerce simplificado, ou sistema de chamados.
